# Architecture

Living document. Each phase updates the sections it makes real (marked ✅) and explains decisions
it locks in.

## 1. Tenancy model — pool database

One Postgres database holds every tenant. Isolation is enforced in application code at the data-
access boundary, with `tenant_id` as a required column on every core table.

```
Tenant (college / university)
 ├─ TenantMember  → User + role (Owner, Admin, Member)
 └─ Club
     ├─ ClubMember → User + role (President, Event_Manager, Member)
     └─ Event
         ├─ Ticket      → User (Registered, Waitlisted, Cancelled)
         └─ Attendance  → Ticket + check-in metadata
```

**Why pool (shared schema) rather than schema-per-tenant?**

- Cross-club features the product needs — a campus-wide "what's on this week" feed, tenant-level
  analytics, one student login across all clubs — are trivial queries instead of cross-schema joins.
- Migrations run once per deploy, not once per tenant.
- The cost is that isolation is a code-level guarantee, so it is treated as a first-class rule
  rather than an afterthought (see §3).

**Hierarchy decisions**

- `User` is a **global** entity (one human, one row) mapped into tenants and clubs through join
  tables. A person is `President` in Club A and `Member` in Club B without any data duplication.
- `Club.tenant_id` is the tenancy root for events. An event's tenant is derived
  (`Event → Club → Tenant`), never passed in from the client.
- Every join table carries a surrogate `id`, a unique constraint on the natural key, and
  `created_at` (and `deleted_at` where membership history matters).

## 2. Data model intent

Implemented in Phase 2 (`prisma/schema.prisma`). Storage rules that hold across tables:

| Concern | Decision |
| --- | --- |
| Identifiers | UUID (v4) primary keys, generated by Prisma — safe to expose in URLs/QR payloads |
| Timestamps | `TIMESTAMPTZ`, **always stored in UTC**; rendered in viewer/tenant timezone |
| Money | (future) integer minor units — never floats |
| Soft deletes | `deleted_at TIMESTAMPTZ NULL` on `Event`, `Club`, `Ticket`; all reads filter `deleted_at IS NULL` by default |
| Capacity | `Event.capacity INT NULL` (null = unlimited) plus `Event.waitlist_enabled BOOL` |
| Ticket secret | `Ticket.qr_code_uuid` is a random UUID, unique-indexed, separate from the ticket id so a ticket id alone can never be used to forge a check-in |
| Audit | `Attendance.checked_in_by` records the staff user; `created_at`/`updated_at` on mutable rows |

Indexes are chosen for the access paths the UI actually uses, e.g.
`Event(club_id, start_time)`, `Ticket(event_id, status)`, `Attendance(event_id, check_in_time)` and a
unique index on `Ticket(event_id, user_id)` to make double-RSVP impossible at the database level.

## 3. Isolation rules (non-negotiable)

1. **No unscoped query.** Every Prisma call touching a tenant-owned table takes an explicit
   `tenantId`/`clubId` filter — no "fetch all then filter in JS".
2. **Tenant comes from the session, never the request body.** A body may name a `clubId`; the
   handler resolves the club, then verifies the session user's membership within that tenant.
3. **Guards run at the route-handler boundary.** Phase 3 adds `requireTenantMember()` and
   `requireClubRole()` helpers that every handler calls before touching data; the helpers throw
   `ApiError.forbidden()` rather than returning booleans that can be forgotten.
4. **404 over 403 for cross-tenant probes.** If a resource exists in another tenant, the API
   answers "not found" so existence is never leaked.
5. **Layer separation.** `app/api/*` handlers do parsing → authorisation → service call and nothing
   else; `lib/services/*` own transactions and Prisma queries; `lib/validation/*` owns Zod schemas.
   This keeps a single auditable place where scoping can be reviewed.

## 4. RBAC matrix (implemented in Phase 3)

| Action | Tenant Owner | Tenant Admin | Club President | Event Manager | Member | Signed-in |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| Create club in tenant | ✅ | ✅ | — | — | — | — |
| Edit club profile | ✅ | ✅ | ✅ | — | — | — |
| Invite / remove club members | ✅ | ✅ | ✅ | — | — | — |
| Create / edit event | ✅ | ✅ | ✅ | ✅ | — | — |
| Publish / cancel event | ✅ | ✅ | ✅ | ✅ | — | — |
| View member-only event | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| RSVP to event | ✅ | ✅ | ✅ | ✅ | ✅ | with a tenant identity |
| Scan / check in attendees | ✅ | ✅ | ✅ | ✅ | — | — |
| View attendance report | ✅ | ✅ | ✅ | ✅ | own ticket | — |
| Soft-delete event | ✅ | ✅ | ✅ | — | — | — |

Role checks are always evaluated as **(user × club × action)** — a global "is admin" flag does not
exist by design.

## 5. Edge-case playbooks

These are the constraints the schema and services are shaped around; each has a phase and a test.

### 5.1 Capacity race conditions (Phase 5)
Five people hitting "RSVP" for the last two seats must produce exactly two registrations.

- Wrap the check in a single interactive transaction:
  `SELECT id, capacity FROM "Event" WHERE id = $1 AND deleted_at IS NULL FOR UPDATE` — the row lock
  serialises concurrent bookings for the *same* event only, so unrelated events stay parallel.
- Inside the lock: count non-cancelled tickets, decide `Registered` vs `Waitlisted`, insert, commit.
- Belt and braces at the database level: `UNIQUE(event_id, user_id)` on tickets and a capacity
  guard in the insert path so a bug in application code still cannot overbook.
- The mutation client never auto-retries (see `query-provider.tsx`) so a timeout can't silently
  double-book.

### 5.2 Offline / poor-network check-ins (Phase 6)
- The scanner validates QR payloads locally (format + signature), so it can keep accepting scans
  while offline.
- Accepted scans go into a durable local queue (IndexedDB, with a `localStorage` fallback) keyed by
  a client-generated `scan_uuid`.
- Sync replays the queue against `POST /api/attendance/sync` as a batch; the endpoint is
  **idempotent** — `scan_uuid` and `ticket.qr_code_uuid` are unique, so replays collapse instead of
  duplicating attendance.
- The UI shows three honest states: synced, pending (n), and rejected (with reasons such as
  "already checked in" or "ticket cancelled"), and never blocks the door on a network call.

### 5.3 Timezones (Phases 2 & 4)
- Postgres stores `timestamptz`; API payloads are ISO-8601 UTC strings.
- `Tenant.timezone` (IANA) is the scheduling default; forms interpret naive input in that zone.
- Rendering happens client-side against the viewer's zone with the tenant zone shown explicitly on
  admin screens, so a "6:00 PM" event is never ambiguous.

### 5.4 Rate limiting (Phase 5)
- Token bucket keyed by `(user_id, action)` for authenticated RSVPs and by IP for public auth
  endpoints, e.g. 10 RSVPs/minute, 30 invites/hour.
- `RATE_LIMIT_DRIVER=memory` uses a per-process store for dev/single instance; `redis` swaps in a
  shared store without changing call sites. Exceeded requests return `429` with `Retry-After` and
  the `RATE_LIMITED` error code.

### 5.5 Soft deletes & data integrity (Phase 4)
- `deleted_at` instead of `DELETE`; attendance and ticket history survive.
- Deleting a club with published events is blocked until the events are cancelled (guarded, with a
  clear error), and cascade rules are explicit per relation rather than implicit.

## 6. API conventions

Every handler returns the same envelope (`src/lib/api/response.ts`):

```jsonc
// success
{ "ok": true,  "data": { /* payload */ } }

// failure
{ "ok": false, "error": { "code": "VALIDATION_ERROR", "message": "…",
                          "details": { "startTime": ["Must be in the future"] } } }
```

- Codes map to fixed statuses: `BAD_REQUEST 400`, `UNAUTHORIZED 401`, `FORBIDDEN 403`,
  `NOT_FOUND 404`, `CONFLICT 409`, `VALIDATION_ERROR 422`, `RATE_LIMITED 429`, `INTERNAL_ERROR 500`.
- **Validation is server-side.** Route handlers parse `await request.json()` with a Zod schema and
  return `422` + field errors on failure; the identical schema powers the React Hook Form resolver
  on the client for instant feedback. Client checks are UX, never a security boundary.
- Unknown throwables are logged with context server-side and returned as an opaque 500 — internals
  are never leaked to the client.
- Handlers stay thin: parse → authorise → service → respond.

## 9. Decision log

| # | Decision | Rationale |
| --- | --- | --- |
| 1 | Prisma over Drizzle | Interactive transactions, mature migration workflow, `$queryRaw` for `FOR UPDATE`; the multi-tenancy strategy is identical either way |
| 2 | Auth.js v5 + join tables over Clerk | No external service or keys required; RBAC matrix lives in our own tables; nothing blocks automated end-to-end verification |
| 3 | Pool tenancy over schema-per-tenant | Cross-club campus feeds and tenant analytics are first-class; migrations stay single-shot |
| 4 | Shared Zod schemas client + server | One definition, two enforcement points; server remains the authority |
| 5 | Single response envelope | Client hooks discriminate on `ok`; error codes map to fixed HTTP statuses |
| 6 | UUID ticket secrets distinct from ticket id | A leaked ticket id cannot forge a check-in |
